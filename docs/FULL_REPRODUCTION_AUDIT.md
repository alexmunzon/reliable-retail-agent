# Full-paper reproduction audit

**Finding:** a full reproduction of the paper has not been run. This document maps the experiments that would need to be reproduced, records what the v1 paper and the two requested author-code revisions actually specify, and marks the settings that cannot be recovered from those sources. No model/API calls were made for this audit. The local gate study and its proposed 1,320-episode extension are separate work and do not reproduce the paper.

The primary paper is Yao et al., *τ-bench: A Benchmark for Tool-Agent-User Interaction in Real-World Domains*, arXiv v1 (17 June 2024), [PDF](https://arxiv.org/pdf/2406.12045), [HTML](https://arxiv.org/html/2406.12045). The paper-era official code revision inspected is [`6f4b718037db619539b8b692060e6686f3f0dcc9`](https://github.com/sierra-research/tau-bench/tree/6f4b718037db619539b8b692060e6686f3f0dcc9), selected as the visible author-repository revision immediately preceding the v1 submission. The requested later comparison is [`59a200c6d575d595120f1cb70fea53cef0632f6b`](https://github.com/sierra-research/tau-bench/tree/59a200c6d575d595120f1cb70fea53cef0632f6b). Neither should be described as a proven snapshot of the authors' executed experiments. Local manifests preserve each checkout's file hashes in `native/source_manifests/paper-era.json` and `native/source_manifests/later.json`.

## What the paper tested

The benchmark has two customer-service domains. Table 1 (§4.1, PDF p. 4) gives τ-retail as 115 tasks over databases with 500 users, 50 products and 1,000 orders, with 7 write and 8 non-write APIs; τ-airline has 50 tasks, 500 users, 300 flights and 2,000 reservations, with 6 write and 7 non-write APIs. In the paper-era source, `tasks.py` is the test/evaluation suite for each domain and contains those 115 and 50 tasks. Retail also has distinct train and dev suites; airline exposes only the test suite in the inspected revision. The paper's reported benchmark results use these complete task suites, not a selected task subset.

The paper reports these experiment families. They overlap, so their episode counts must not be added as though each plot represented a disjoint dataset.

Table 2 names the model profiles as `gpt-4o`, `gpt-4-turbo`, `gpt-4-32k`, `gpt-3.5-turbo`, `claude-3-opus`, `claude-3-sonnet`, `claude-3-haiku`, `gemini-1.5-pro-latest`, `gemini-1.5-flash-latest`, `mistral-large`, `open-mixtral-8x22b`, and `meta-llama-3-70B-instruct` (§5, PDF pp. 5–6). The paper says models were accessed through OpenAI, Anthropic, Google, Mistral and AnyScale APIs. Its API-facing names are not equivalent to immutable model snapshots. The author CLI at the selected commit includes dated choices for some OpenAI and Claude models, but the paper does not map all result labels to a dated ID; several profiles are moving aliases. Figure 4 explicitly labels `gpt-4-32k-0613`, whereas Table 2 labels it `gpt-4-32k`.

The user simulator is a single model profile, GPT-4-0613 (§3); the paper does not compare user-simulator models. The paper does report an approximate cost decomposition for retail gpt-4o FC paired with GPT-4 user simulation (§5.1), but this is not a user-simulation ablation. A reproduction should not invent a simulator-comparison experiment or attribute the gate study's two-arm contrast to one.

## Method, sampling, and metrics specified by the paper

The environment is a tool-agent-user interaction loop. Tasks provide a natural-language instruction plus reference write actions and, for some tasks, required output strings. At the end of the conversation, the reward checks both the database state induced by the agent's write actions and whether the agent told the user required information (§3, PDF pp. 2–4). The paper's setup hides the full instruction from the agent and supplies it to the simulated user. The paper describes a stochastic user simulator that emits varied utterances for the same scenario; it does not claim a controlled user-model comparison.

The main agent method is zero-shot FC: the domain policy is the system prompt, and each agent turn chooses either a user response or a tool call. The paper compares text-formatted ReAct (`Thought` plus an `Action` in JSON form) and Act-only (action without reasoning), and reports that a `think` function did not improve FC (§5.1). Each task is capped at 30 agent actions. The reported temperatures are 0.0 for the agent and 1.0 for the user. Table 2 uses at least three trials per task; this is a minimum, not an exact shared count. The pass^k plot includes k through 32. Appendix Figure 7 specifies more than 40 gpt-4-turbo trials per retail task for its diagnostic.

For a task with `n` trials and `c` successes, the paper defines `pass^k` as the task-average of `C(c,k)/C(n,k)` and `pass@k` as one minus the task-average of `C(n-c,k)/C(n,k)` (§3, PDF pp. 3–4). These estimate the probability that all k sampled trials succeed versus at least one of k sampled trials succeeds. `pass^1` is mean reward. Table 2's “avg” is weighted by domains rather than by task count. A missing, censored, or nonterminal trajectory cannot be silently coded as reward zero or dropped from a paired denominator; the original paper does not describe such an incomplete-run policy because its published aggregates do not include raw attempt records.

## What the two source revisions establish

The paper-era tree is the defensible author-source starting point: the local audit verified 70 tracked files and their SHA-256 digests at commit `6f4b718…`. Its `run.py` exposes the two domains, test/train/dev split option, model choices, FC/ReAct strategies, temperature default 0, user-model argument default `gpt-4`, `--num_trials` default 1, seed default 10, and task-range controls. `tau_bench/agents/gpt_function_calling_agent.py` loops for at most 30 turns. `tau_bench/envs/user.py` uses temperature 1 and max_tokens 150 for the simulated user. `tau_bench/envs/base.py` evaluates database outcomes and required output substrings. These details support the broad paper method, but defaults do not themselves reconstruct the paper experiments: in particular the CLI default of one trial is below the Table 2 minimum.

The same tree's user-model default is the alias `gpt-4`, while the paper identifies the simulator as `gpt-4-0613`. This is a documented paper/source mismatch in the visible source, not proof that the authors used the default alias in their runs. Likewise, the CLI's exact candidate IDs do not resolve every model label in the paper. The run script's default `--seed 10` seeds Python's `random` module; API sampling is controlled by provider/model behavior, and the paper provides no per-episode seeds or saved run manifests. The code's `--num_trials` default, run timestamp outputs, and run-time aliases leave exact original trial profiles and model resolutions unproven.

Commit `59a200c…` is a much later code state, not a second paper reproduction snapshot. Its verified manifest has 113 tracked files. It adds/reworks runtime/model plumbing, includes later test-task files and historical trajectory data, and changes source hashes across tasks, users, tools, agents, and run logic. Those files may be useful as a comparator, but substituting them changes the source/data condition. The local audit did not treat later trajectories as v1 results or merge the two trees. The two manifests are the exact local evidence for the trees inspected.

## Limits and unresolved requirements

The principal missing evidence is the authors' run-level record: exact model snapshot for each result, provider/model routing and API parameters, task-by-task trial count, seeds or independent sampling protocol, successful and failed raw trajectories, token/cost records, and exact run date. The paper says “at least 3” trials for Table 2 but does not disclose the exact n per task; the pass^k chart's k range does not supply the individual trial matrix. It does not state the exact run count for Figure 3 or Table 3. It does not publish the task-level failure labels or the four pre-fix task instructions needed to exactly reconstruct Figure 5. In the code, one can set a Python seed and select an alias, but neither proves the unpublished choices.

The v1 paper identifies GPT-4-0613 as user simulator; paper-era `user.py` accepts a model argument and defaults to `gpt-4`, and the run wrapper passes that alias by default. Reconstructing the original provider resolution from a present-day alias would be an undocumented substitution. Some listed actor models have no explicit dated snapshot in the paper; the paper-era code contains provider aliases and selected dated identifiers, but no paper-to-CLI mapping for every table entry. At least the GPT-4-32k profile is no longer available from the original provider as of 2025; it cannot be invoked as the historic service snapshot. We did not replace any of these with a newer model.

The visible author revision was chosen because it is the latest visible official ancestor before the v1 submission, but the manifest itself correctly records `exact_paper_run_snapshot_proven: false`. The authors may have used unpublished local edits or a different later API snapshot. The later comparator commit does not close that gap. Source and paper agreement on broad task counts, 30 action cap, temperature settings, method families, and end-state evaluation is high-confidence; exact historical model identity and actual sampling are unknown.

The custom confirmation-gate experiment is separate from this paper reproduction audit. Its current version is unevaluated, and no benchmark-wide improvement or full paper reproduction is claimed. This publication contains offline code checks and a separately labeled analysis of later author-released trajectories. No paid calls were made for this audit.
